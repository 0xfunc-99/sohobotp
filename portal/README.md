# multiOTP management portal

Server-rendered PHP portal that replaces the legacy multiOTP admin page. It reuses the
multiOTP engine (`multiotp.class.php`) for users, tokens and LDAP, and adds named
administrators, roles, administrator MFA, hardened sessions, CSRF protection and a
tamper-evident audit trail.

Served at `https://<host>/portal/`. Only `portal/index.php` and `portal/assets/` are public;
nginx refuses `portal/src`, `portal/templates`, `portal/bin` and `portal/tests`, and every file
in those folders also refuses to run on its own.

## First administrator

There is no default password. Create the first super administrator from the command line:

```sh
# Docker
docker exec -it <container> php /usr/local/bin/multiotp/portal/bin/portal-admin.php create --username=alice --role=superadmin --display-name="Alice Example"
# Appliance / source tree
php portal/bin/portal-admin.php create --username=alice --role=superadmin
```

It prints a temporary password (valid 24 h). At first sign-in the administrator scans a QR
code with an authenticator app, then must choose a new password.

Other commands: `list`, `reset-password`, `reset-mfa`, `unlock`, `enable`, `disable`
(all with `--username=`), and `verify-audit`. Use them to recover when no super
administrator can sign in. Every command is written to the audit trail as `cli:<system user>`.

## Roles

| Role | Can do |
|---|---|
| Super administrator | Everything, including administrator accounts |
| Administrator | Users, tokens, directory settings and sync, RADIUS, endpoints, audit trail (not administrator accounts) |
| Helpdesk | Look up users, unlock accounts, resync tokens, enrol authenticators and recovery codes |
| Auditor | Read-only, including the audit trail and directory settings |

Permissions for stages 2–4 are already defined in `src/Roles.php`; their pages arrive with those stages.

## Users and tokens

- **Users** page: search (name, email, group, token), status filter (enabled, disabled, locked,
  from directory, local), paging, and bulk unlock / enable / disable / delete.
- **New user** (local accounts not in the directory): software TOTP token with a random seed,
  shown once as a QR code, or an unassigned hardware token.
- **User page**: unlock, enable/disable, edit, delete, enrol a new authenticator (QR shown once),
  10 new recovery codes (shown once, single use), resync a token with two consecutive codes,
  assign or remove a hardware token.
- **Hardware tokens** page: inventory, import (PSKC plain/encrypted, multiOTP CSV, Yubico,
  Alpine, Authenex, via the multiOTP importers, max 5 MB), delete unassigned tokens.
- Seeds and recovery codes are generated by the portal with `random_bytes()`/`random_int()`
  (the engine's own helpers use md5/mt_rand) and are never written to the audit trail.

## Directory (AD/LDAP)

Settings are stored in the multiOTP configuration, so RADIUS and the CLI use them too:
servers, port, LDAPS and certificate check, base DN, users OU(s), bind DN, account suffix,
group scope (Active Directory), LDAP filter, nested groups, groups without 2FA and opt-in,
attribute mapping, token type for new users, password + OTP, and the lifecycle rules.

**Service-account password**: sealed in `directory.json` with the portal key and handed to the
engine only in memory during a test, preview or sync. It is removed from the multiOTP
configuration (where it was only obfuscated); RADIUS logins do not need it because they bind
as the user. A password saved earlier by the legacy GUI or CLI is migrated at the first save.
Consequence: `multiotp.php -ldap-users-sync` from cron no longer has the password; use the
portal schedule instead.

**Lifecycle** (multiOTP engine rules, shown on the page):
- disabled in the directory → disabled in multiOTP at the next sync (unless "keep enabled");
- enabled again → re-enabled (unless "do not re-enable");
- no longer in the directory or out of scope → disabled, then deleted after the retention
  period (default 30 days, 0 = never).

**Test connection** binds with the service account (in the request). **Preview changes**
reads the directory and lists who would be created, disabled, re-enabled or is no longer
found, without changing anything. **Sync now** and the **schedule** run the engine's
`SyncLdapUsers()`. Both preview and sync run in the background worker; the job page shows live
progress (including the engine's "LDAP account #N" counter), lets you stop a sync, and keeps
the result: users created, disabled, re-enabled, deleted, plus the engine messages. The last
200 jobs are kept.

Known engine limits:
- Generic LDAP only lists entries with `objectClass=posixAccount` (or `user`).
- Group lists only work with Active Directory; with generic LDAP they crash the engine, so the
  portal refuses them. Use the LDAP filter instead, e.g.
  `(&(objectClass=posixAccount)({cn_identifier}={username})(memberOf=cn=MFA,ou=groups,dc=example,dc=org))`.
- Fixed in this stage: the LDAP filter option was never applied (the engine looked up the key
  `"ldap_filter "` with a trailing space). Fixed in `contrib/MultiotpAdLdap.php` and every bundle.

## RADIUS servers (FreeRADIUS)

**Server groups** (e.g. VPN, firewalls, Wi-Fi) hold the login policy; every server in a group
inherits it:
- **challenge-response**: the user types the password or PIN, FreeRADIUS answers with an
  Access-Challenge, the user types the code (optionally sent by SMS); custom challenge texts;
- **result caching** for devices that re-authenticate often (weakens 2FA, off by default);
- ignore PIN / directory-password prefixes (code only) for these servers;
- do not send the user's multiOTP group in the reply.

**Servers** (RADIUS clients): name, IP address or network (host names refused, nothing larger
than /8, network addresses aligned), group, device type, "require Message-Authenticator"
(on by default, against BlastRADIUS). The **shared secret** is generated (24 random characters)
or entered, shown **once**, sealed in `radius.json`, and can be rotated.

Each server is written to the engine as a multiOTP *device* (short name `<name>-<id>`, which
FreeRADIUS passes to multiOTP), so the engine applies the group policy at login.

**Apply** (background job): the portal writes a candidate client file and runs the root helper
`/usr/local/sbin/multiotp-portal-radius apply` through sudo. The helper
- accepts only fixed commands, no arguments (sudoers lists each exact command line);
- re-validates **every line** of the candidate against the generated grammar (so `$INCLUDE`,
  modules or anything else is refused);
- installs it as `/etc/freeradius/3.0/multiotp-portal-clients.conf` (root, mode 0640), adds one
  `$INCLUDE` line to `clients.conf`, runs `freeradius -C`, and restarts FreeRADIUS;
- restores the previous files if the check fails, so a bad change never stops RADIUS.

The helper is installed root-owned outside the web-writable `/usr/local/bin/multiotp` tree by
`install.sh` (the copy in `portal/bin/` is never run through sudo).

**Diagnostics** page: FreeRADIUS running or not, pending changes, last apply output, a warning
and a one-click fix when the install-time catch-all client (`0.0.0.0/0`, secret
`myfirstpass`) is still active, a **test login** that sends a real Access-Request through
FreeRADIUS (from 127.0.0.2 with its own secret), and the recent accepted/rejected logins from
the multiOTP log.

**Per-user login format** (user page): code only, PIN + code (a random 6-digit PIN shown once),
or directory password + code (users synced from AD/LDAP only).

Not yet possible: restricting which user groups may sign in through a server group (needs an
engine change; planned).

## Endpoints (Windows and Linux agents)

Design: [docs/endpoints.md](docs/endpoints.md). Exact agent protocol, with libsodium test
vectors: [docs/agent-protocol.md](docs/agent-protocol.md). Stage 4a is the portal side; the Go
agent itself is built separately (`portal/tasks/codex-agent.md`).

- **Endpoint groups** hold the policy:
  - Linux: which services need a code (SSH, sudo, console, su), the RADIUS server group the
    machines join, RADIUS servers, excluded users and groups (root always), and whether SSH
    keys also need a code;
  - Windows (multiOTP Credential Provider): sign-in, unlock and UAC modes, a break-glass
    account, offline cache (opt-in, 1-30 days), UPN format and texts;
  - the check-in interval.
- **Enrolment tokens** (Enrol endpoints page) are per group, expire (1-720 h), have a use limit,
  are shown once and stored as SHA-256 hashes. The page shows the install command and the
  **portal key pin**: agents refuse any portal whose signing key does not match it.
- **Agent API** `portal/agent.php?a=enroll|checkin` (the second public PHP file):
  - no session or cookies;
  - every check-in is signed with the machine's own Ed25519 key, refused when more than
    5 minutes old, replayed, tampered or from a disabled machine;
  - failed tokens and signatures are throttled per IP.
- **Configuration** is versioned per endpoint and signed with the portal key (seed sealed with
  `portal.key`). Secrets are sealed to the machine's X25519 key:
  - the Linux endpoint's RADIUS secret;
  - a per-endpoint Credential Provider secret.

  A policy change or a RADIUS secret rotation pushes a new version at the next check-in. A
  failed apply is reported to the endpoint page and not retried until the policy changes.
- **Linux endpoints become RADIUS clients** (their enrolment address, their own secret) in
  the group's RADIUS server group, and FreeRADIUS is re-applied automatically. Disabling,
  deleting or moving a machine to a group without Linux 2FA removes the client.
- **Endpoints page**: online/offline (3 missed check-ins), needs attention (apply failed,
  no RADIUS client), inventory (OS, IPs, agent and login component versions), configuration
  wanted vs applied, move, disable (also replaces its secrets), delete.
- **Approval of new machines** (per token): active immediately, approved by an administrator,
  or approved automatically when the computer account is in Active Directory (enabled, DNS
  name resolving to the enrolment address, not already used). Pending machines check in but
  get no configuration or secrets.
- **Policy from Active Directory**: rules map a computer's OU or (nested) AD group to an
  endpoint group, first match wins, re-checked every 15 minutes and after enrolments
  (worker job `endpoints.directory`, "Check AD now"). Administrator moves are pinned. Rollout
  with Group Policy: see [docs/endpoints.md](docs/endpoints.md#rollout-from-active-directory-group-policy).
- **Credential Provider gateway** `portal/cp.php?e=<endpoint>` (stage 4c): the multiOTP
  Credential Provider on each Windows machine talks to its own URL with its **own secret**
  (pushed sealed by the agent), answered by the engine's client/server code. The offline
  cache follows the endpoint group (off, or 1-30 days); unknown, pending, disabled and Linux
  endpoints are refused; the last sign-in request is shown on the endpoint page.
- **Signed self-update** (4d): `portal-admin.php agent-release-add` stores releases signed
  offline (`sohobotp-agent release sign`); the endpoint group's *Agent version* rolls them
  out; agents verify the signature with the release key built into them.
- Not yet: TLS verification in the CP's bundled client (see docs/endpoints.md).

## Background worker

`portal/bin/worker.php` runs queued jobs and the scheduled sync. One worker at a time (lock
file); jobs left "running" by a crashed worker are marked failed.

- Docker image: started by `newvm.sh` as `www-data`, restarted if it stops; output in
  `/var/log/multiotp/portal-worker.log`.
- Appliance (systemd): `multiotp-portal-worker.service`, created by `install.sh`.
- Elsewhere: `php portal/bin/worker.php --loop` as the web server user, or `--once` from cron
  every minute.

## Administrator MFA

Every administrator needs a second factor; there is no way to skip it.

- **Authenticator app** (default): a TOTP secret enrolled in the portal and stored
  encrypted (libsodium, key in `portal.key`). It is *not* a multiOTP user, so it can never be
  used to sign in over RADIUS.
- **Existing multiOTP user**: the administrator's own multiOTP token (for example their
  directory account), checked by the multiOTP engine with its PIN, lockout and replay rules.
  without2FA users are refused.

## Security behaviour

- HTTPS only (plain HTTP is refused unless `MULTIOTP_PORTAL_ALLOW_HTTP=1`, for local tests).
- Session cookie `__Host-motp_portal`: Secure, HttpOnly, SameSite=Strict; strict mode; new id at
  every privilege change; 15 min idle and 8 h absolute timeout.
- Changing a password, resetting MFA, disabling an account or "Sign out" bumps the account's
  session version, which ends all its other sessions immediately.
- CSRF token on every POST plus an Origin/Referer same-host check.
- 5 wrong passwords or codes lock the account for 15 min; 20 failures from one IP in 15 min
  block that IP. Error messages never reveal whether an account exists.
- Passwords: Argon2id, at least 12 characters, not containing the username.
- The last active super administrator cannot be disabled or demoted; nobody can disable
  themselves or reset their own second factor.
- Strict Content-Security-Policy (no inline script), `X-Frame-Options: DENY`, `no-store`.

## Audit trail

`audit.jsonl` in the data folder: one JSON object per line, each with the SHA-256 hash of
the previous one. The Audit trail page (and `portal-admin.php verify-audit`) re-checks the
chain and reports the first modified or deleted line. Fields named like passwords, secrets,
seeds, OTPs, PINs or keys are written as `[redacted]`.

## Files and settings

Data folder: `/etc/multiotp/portal/` on the appliance and in Docker (inside the persistent
`/etc/multiotp` volume), `config/portal/` in a source checkout. It holds `admins.json`,
`audit.jsonl`, `throttle.json` and `portal.key`, all mode 0600. **Back up `portal.key`
together with `admins.json`**: without it, authenticator-app enrolments cannot be read and
administrators must re-enrol.

Environment variables (all optional): `MULTIOTP_PORTAL_DATA`, `MULTIOTP_ETC_DIR`,
`MULTIOTP_LOG_DIR`, `MULTIOTP_PORTAL_BRAND`, `MULTIOTP_PORTAL_COMPANY`, `MULTIOTP_PORTAL_ISSUER`, `MULTIOTP_PORTAL_IDLE_TIMEOUT`,
`MULTIOTP_PORTAL_ABSOLUTE_TIMEOUT`, `MULTIOTP_PORTAL_MAX_FAILURES`, `MULTIOTP_PORTAL_LOCKOUT`,
`MULTIOTP_PORTAL_IP_MAX_FAILURES`, `MULTIOTP_PORTAL_IP_WINDOW`,
`MULTIOTP_PORTAL_TEMP_PASSWORD_LIFETIME`, `MULTIOTP_PORTAL_MIN_PASSWORD_LENGTH`,
`MULTIOTP_PORTAL_ALLOW_HTTP` (tests only). Requires PHP 8.1+ with sodium and mbstring.

**Branding.** The portal uses the Sohobcom identity: logo `assets/brand-logo.png`, icon
`assets/brand-icon.png` (favicon), colours navy `#0163AD`, sky `#05A8E8` and aqua `#4CC0D9`
(CSS variables `--brand-*` at the top of `assets/portal.css`, with a dark-mode variant).
The product is called **SohobOTP**: `MULTIOTP_PORTAL_BRAND` sets the product name in the header
and page titles (default `SohobOTP`), `MULTIOTP_PORTAL_COMPANY` the logo's text alternative

## Changes to the legacy code in this stage

- `multiotp.server.php`: CORS no longer reflects any origin with credentials; only origins
  listed in `MULTIOTP_CORS_ORIGINS` get CORS headers.
- `ApiVueJsPreAuth()`: no longer adopts a session id sent in the request body (session
  fixation); SameSite=Strict, strict mode.
- `ApiLogin()`: the OTP-administrator path used an undefined variable and never selected the
  user; fixed (OTP read from `password`), and the session id is regenerated after login.

These are applied to every copy: `multiotp.class.php`, the generated `multiotp.php`, and
the appliance bundles under `raspberry/boot-part/multiotp-tree/usr/local/bin/multiotp/`.

### Anonymous statistics off (all engine copies)

multiOTP sent anonymous usage statistics to `stats.multiotp.net` once a week, from inside
a login check, with a 5-second timeout: the first VPN/SSH login of the week could be slow or
time out (seen in the agent end-to-end test), and the appliance contacted an outside server.
SohobOTP turns this off:

- the engine default `anonymous_stat` is now 0 in every copy (new installations);
- the appliance start script runs `portal-admin.php anonymous-stats --state=off --once`, which
  switches existing installations off once and then respects an administrator's choice;
- `portal-admin.php anonymous-stats [--state=on|off|status]` changes or shows it (audited).

### Stage 4c (both server copies)

- `multiotp.server.php` and the appliance `index.php`: client/server (Credential Provider)
  mode is refused while the server secret is empty or the public default
  `ClientServerSecret`, unless `MULTIOTP_ALLOW_DEFAULT_SERVER_SECRET=1`. Managed Windows
  machines use `portal/cp.php` with their own secrets; an existing legacy rollout must set
  a private global secret first.

### Engine fixes in stage 3 (all copies)

- `CheckUserLdapPassword()` wrapped every login DN without `cn=` as `CN=<dn>,<base DN>`, so
  "directory password + code" never worked with generic LDAP (`uid=...` DNs). Only bare account
  names are wrapped now.
- `CheckToken()` never read the device's challenge-response settings, so per-server challenge
  mode had no effect (only the global setting worked). It now uses them.
- `MultiotpAdLdap` appended the account suffix to every bind name, so a synchronized AD user
  bound as `CN=alice,OU=...,DC=...@DOMAIN` and "AD password + code" was always refused
  (AD error 52e). A DN, UPN or `DOMAIN\user` is now used as is (`BindName()`).
- `SyncLdapUsers()` created new users without their display name (`FastCreateUser()` has no
  such parameter); it is now stored at creation instead of on the next sync.
- Portal: the engine only disables users whose `synchronized_time` is older than the sync
  start (whole seconds), so the portal waits for the next second if the previous sync
  finished in the current one.

## Tests

```sh
sh portal/tests/run-in-docker.sh
```

Builds a PHP 8.4 image with ldap/bcmath (`tests/docker/php.Dockerfile`) and a throwaway
OpenLDAP directory (`tests/docker/ldap/`, users alice/bob/carol in `mfa-users`, dave in
`contractors`), then runs PHP lint, `tests/unit.php` and `tests/e2e.php` with the worker
running. The end-to-end checks cover sign-in, enrolment, roles, CSRF, lockout, session
revocation, TOTP replay, the audit trail, the legacy CORS/session fixes, user creation with
a seed checked by the multiOTP engine, recovery codes, disable/unlock, bulk actions, token
import and assignment, directory test/preview/sync through the worker, out-of-scope users
being disabled, and the helpdesk limits. Stage 4 adds the agent protocol test vectors,
enrolment, signed check-ins (replay, tampering, clock skew, other key, disabled endpoint),
configuration versions and secret sealing, RADIUS clients for Linux endpoints, and the
endpoint pages, using a simulated agent (`tests/AgentSim.php`).

**Production image test** (real nginx, PHP-FPM, FreeRADIUS, sudo helper, worker):

```sh
sh portal/tests/run-appliance-test.sh
```

Builds the root `Dockerfile` and checks HTTPS behind nginx (headers, `__Host-` cookie, HSTS,
internal paths refused, HTTP redirect), the worker running as `www-data`, and, through real
FreeRADIUS: apply with config check and restart, accept/reject, per-server secrets, unknown
sources ignored, secret rotation, challenge-response per group, PIN + code, and disabling the
catch-all client. Then a simulated Linux agent enrols and checks in through nginx, becomes a
FreeRADIUS client, and logs in with the secret it received; once disabled it is refused by both
the API and FreeRADIUS; a simulated Windows machine signs in through `cp.php` (offline cache
stored), and the legacy root URL refuses the default secret. The first build downloads the Debian stack (slow); later builds are cached.

## Active Directory tests

```sh
MULTIOTP_TEST_AD=1 sh portal/tests/run-in-docker.sh
```

Adds a disposable Samba AD DC (`EXAMPLE.TEST`) after the normal OpenLDAP tests.
The AD suite uses a separate PHP container, trusted self-signed LDAPS certificate,
portal `Directory` settings and real worker jobs. It checks preview/sync, user
attributes, direct/multiple/nested group scopes, disabled and re-enabled accounts,
out-of-scope disabling, directory password + TOTP, and service-password storage.
TLS checks include `never`, trusted `demand`, and rejection of an untrusted certificate.
The default run does not build or start Samba.

See [the Samba fixture](tests/docker/samba/README.md) for public test credentials,
xattr requirements and the test-only `SYS_ADMIN` capability. No host ports are
published. The first optional run downloads a Debian image and Samba packages;
do not run it when downloads are prohibited. If buildx settings are unwritable,
set `BUILDX_CONFIG` to a writable temporary directory.

`tests/e2e-ad-endpoints.php` (same run) checks computer lookups in OUs and nested groups,
approval from AD (unknown, disabled, wrong-address and duplicate computers stay pending),
rule order, AD membership changes, administrator pinning and identity binding (27 checks).

**Validation status (2026-11-09):** all 87 Samba AD checks and 27 endpoint AD checks pass, together with the
default suite. Running them found three bugs, fixed in this stage (see below): the Samba
image missed `samba-ad-provision`, new AD users had no display name until the second sync,
and AD password + code always failed when an account suffix was set. A fourth issue
(two syncs in the same second never disabled out-of-scope users) is handled in the portal.
